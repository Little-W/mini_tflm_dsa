# im2col 输入缓存容量与卷积尺寸

## 配置与作用

`IM2COL_CACHE_BYTES` 设置硬件 im2col 使用的原始输入数据缓存。共享 DMA 的图像读取也使用这项缓存。数据 RAM 与共享 IA/PS RAM 分别计量，容量设置不会改变 `SHARED_BANK_BYTES` 或 `SHARED_BANK_COUNT`。

在 `config/npu.mk` 或 `config/npu_fpga.mk` 中设置：

```make
IM2COL_CACHE_BYTES ?= 4096
```

支持 512、1024、2048、4096、8192、16384、32768、65536 字节。默认值为 4096 字节。缓存采用两路组相联结构，每条缓存行包含 16 字节数据，因此：

$$N_{set}=\frac{B_{cache}}{2\times16}.$$

缓存容量在构建时确定。驱动在初始化时读取硬件报告的实际容量，将该容量用于卷积调度评分。模型初始化计算的 WS/IS、R/W 和 IA/PS 配置继续保存在 arena。

```bash
make menuconfig
make capacity-show IM2COL_CACHE_BYTES=8192
make capacity-check IM2COL_CACHE_BYTES=8192
```

`menuconfig` 的 `im2col data cache` 项支持选择容量；按 `?` 显示当前容量对应的卷积窗口尺寸。`capacity-show` 输出 `im2col_cache_guidance`，同时报告数据、标签与缓存行使用状态所占的容量。命令行覆盖只作用于该次 Make 调用；保存配置使用 `menuconfig` 的 Save。

## 容量统计

每条缓存行的元数据包含一份 28 位地址标签、两份 13 位窗口编号、三份 32 位使用位置、一位有效状态，以及三个两位来源存储体，共 157 位。三个来源存储体的异或值用于选择使用位置，分别支持填充、提示和命中更新。下表统计声明的数据位，多读端口实现所需的存储复制及 FPGA 存储块的深度、位宽取整由综合结果统计。字段定义见 [`conv_windowed_cache`](../rtl/npu/dma/cache/conv_read_cache.sv)。

| 数据容量 | 集合数 | 标签及使用状态 | 数据与状态合计 |
|---|---:|---:|---:|
| 0.5 KiB | 16 | 628 B | 1,140 B |
| 1 KiB | 32 | 1,256 B | 2,280 B |
| 2 KiB | 64 | 2,512 B | 4,560 B |
| 4 KiB | 128 | 5,024 B | 9,120 B |
| 8 KiB | 256 | 10,048 B | 18,240 B |
| 16 KiB | 512 | 20,096 B | 36,480 B |
| 32 KiB | 1,024 | 40,192 B | 72,960 B |
| 64 KiB | 2,048 | 80,384 B | 145,920 B |

请求队列、响应队列和预取队列在容量模型中单独统计。`CAPACITY_BUDGET_BYTES` 检查包含这些队列、缓存状态及 NPU 其他缓冲。增加输入缓存后，可以通过 `capacity-check` 查看整个配置是否满足预算。

## 如何对应卷积尺寸

卷积核大小只决定输入工作集的一部分。还需考虑输入宽度、输入通道数、S8/S16 类型、dilation、地址位置及每次处理的空间窗口。以下分开说明完整输入数据容量和当前 K16 通道片段的滑动窗口容量。

### 完整输入数据

对于 `H × W × C` 的 NHWC 输入，数据字节数为：

$$B_{input}=H\,W\,C\,e,\qquad e=1\text{（S8）或}2\text{（S16）}.$$

`B_input <= IM2COL_CACHE_BYTES` 是完整输入的数据容量条件；实际常驻还要检查同一集合的缓存行数量。例如 `16 × 16 × 16` 的 S8 输入为 4096 B，S16 为 8192 B。RGB 输入 `96 × 96 × 3` 的 S8 数据为 27648 B。

启用空间索引要求输入首地址为 16 字节整数倍，且每像素字节数满足以下任一条件：它是 16 的整数倍，或它是小于 16 的二次幂。其他情况使用物理地址缓存行的 XOR 索引。RGB 三通道输入采用后者。地址与通道片段条件见 [`conv_im2col_frontend.sv`](../rtl/npu/conv/conv_im2col_frontend.sv)。

### 一个 K16 通道片段的输入行带

以下表格适用于普通非分组 NHWC 卷积：输入首地址和 K16 通道片段起点为 16 字节整数倍，输入通道数为 16 的整数倍。每次处理 16 个通道时，每个像素的当前片段分别需要一条 S8 缓存行或两条 S16 缓存行。

该结构把像素位置映射为 `pixel_index mod N_set`，不同通道片段使用同一集合的两路。设当前完整输入行带包含 `P` 个像素，当前片段每像素需要 `F` 条缓存行，则最大集合占用为：

$$L_{set}=\left\lceil\frac{P}{N_{set}}\right\rceil F,\qquad F=1\text{（S8）或}2\text{（S16）}.$$

当前片段的行带在 `L_set <= 2` 时满足集合容量条件。对于输入高度不少于有效卷积核高度的情况，采用包含 dilation 间隔和全部输入列的保守行带：

$$H_{eff}=1+(K_h-1)D_h,\qquad P=H_{eff}W_{in}.$$

下表列出 dilation 为 1 时，一个行带可容纳的最大输入宽度。每项均为 `S8 / S16`，描述当前片段的容量，不包含全部通道同时常驻。

| 缓存数据容量 | 3 × 3 最大输入宽度 | 5 × 5 最大输入宽度 | 7 × 7 最大输入宽度 |
|---|---:|---:|---:|
| 0.5 KiB | 10 / 5 | 6 / 3 | 4 / 2 |
| 1 KiB | 21 / 10 | 12 / 6 | 9 / 4 |
| 2 KiB | 42 / 21 | 25 / 12 | 18 / 9 |
| 4 KiB | 85 / 42 | 51 / 25 | 36 / 18 |
| 8 KiB | 170 / 85 | 102 / 51 | 73 / 36 |
| 16 KiB | 341 / 170 | 204 / 102 | 146 / 73 |
| 32 KiB | 682 / 341 | 409 / 204 | 292 / 146 |
| 64 KiB | 1365 / 682 | 819 / 409 | 585 / 292 |

常用尺寸的配置起点如下，输入高度假设足够覆盖有效卷积核高度：

| 卷积与输入类型 | 输入宽度 | 当前片段行带建议容量 |
|---|---:|---:|
| 3 × 3，S8，C 为 16 的整数倍 | 32 | 2 KiB |
| 3 × 3，S8，C 为 16 的整数倍 | 64 | 4 KiB |
| 3 × 3，S8，C 为 16 的整数倍 | 128 | 8 KiB |
| 3 × 3，S16，C 为 16 的整数倍 | 32 | 4 KiB |
| 3 × 3，S16，C 为 16 的整数倍 | 64 | 8 KiB |
| 5 × 5，S8，C 为 16 的整数倍 | 64 | 8 KiB |
| 3 × 3，dilation_h=2，S8，C 为 16 的整数倍 | 64 | 8 KiB |

1 × 1 卷积沿空间维度没有相邻卷积窗口的重叠，参数选择主要考虑矩阵复用、总线传输及写回。较大输入缓存的收益需要结合实际调度测试。

### 通道片段预取和实际调度

对于每像素至少 16 字节的输入，当前与后继 S8 通道片段可以分别使用两路。硬件要求 `H × W <= N_set` 才启用整幅空间范围的后继片段预取，并同时检查通道片段起点、剩余通道数和当前请求形状。这个空间条件与完整输入的字节条件分别检查。

例如 4 KiB 对应 128 个集合。`10 × 10 × 64` 的 S8 输入有 100 个空间位置，能够满足上述空间条件；完整输入为 6400 B，仍需分片处理通道。

R/W 调度会改变在返回某个位置之前访问的空间范围。stride、padding 和预取也会改变实际访存量。上述表格用于选择待比较的容量；最终选择使用实际模型形状、真实张量地址和相同内存时序的 RTL 周期。

## RTL 缓存测试示例

以下结果来自生产版 `conv_im2col_frontend` 与窗口缓存的 RTL 仿真，采用 32 位 AXI、开启预取，并通过存储器与输出端的随机等待检查传输。描述符按照 DW 使用的通道片段、输出位置、卷积核位置顺序提交。周期统计覆盖前端完成全部描述符所需的时间，包含缓存清理和等待；计算阵列与完整网络执行另行测量。输入均为 S8，stride 和 dilation 均为 1。

每个单元格依次给出外部读取字节数和前端周期数：

| 输入与卷积核 | 512 B 缓存：读取 B / 周期 | 4 KiB 缓存：读取 B / 周期 | 64 KiB 缓存：读取 B / 周期 |
|---|---:|---:|---:|
| `32 × 32 × 8`，3 × 3 | 144,048 / 125,096 | 8,192 / 49,297 | 8,192 / 51,214 |
| `8 × 8 × 64`，3 × 3 | 4,096 / 16,462 | 4,096 / 16,377 | 4,096 / 18,240 |
| `8 × 8 × 16`，1 × 1 | 1,024 / 907 | 1,024 / 988 | 1,024 / 2,960 |

`32 × 32 × 8` 的 3 × 3 工作集从 512 B 增至 4 KiB 后，外部读取降为输入数据的 8,192 B。`8 × 8 × 64` 的当前通道片段窗口较小，512 B 缓存已经能够使外部读取保持为 4,096 B；完整输入大于缓存，仍然可以在按片段处理时获得充分复用。

这组测试中的九种输入在 4 KiB 与 64 KiB 下具有相同的外部读取字节数。缓存每次重新配置时按集合清理状态，集合数从 128 增至 2,048 会增加清理时间。1 × 1 示例中三种容量均读取 1,024 B，512 B 的前端周期最少。因此建议先选择能容纳实际窗口的容量，再测量相邻容量，结合整个 NPU 的容量预算选择配置。

本次检查覆盖全部八种容量，共 296 个前端任务、2,880 个 tile，并在三种容量下完成 27 个流量测试。各项均检查输出数据和外部读取计数。完整流量结果、源文件摘要和运行信息见 [测试数据](measurements/im2col_cache_configuration_20261117.json)，测试程序见 [`run_cache_profiles.py`](../test/im2col_cache_config/run_cache_profiles.py)。

## 检查方法

```bash
make capacity-test
python3 test/im2col_cache_config/run_cache_profiles.py
python3 test/conv_npu/run.py --help
python3 test/conv_frontend/tools/run_rtl.py --help
```

容量测试检查配置文件与环境变量优先级、菜单保存、生成的 C 宏、完整缓冲容量和卷积尺寸提示。行带提示由 [`im2col_cache.py`](../scripts/capacity/im2col_cache.py) 计算，[独立集合枚举测试](../test/capacity/test_im2col_cache_config.py)逐项检查 S8/S16、dilation、紧凑小通道和地址条件。RTL 的完整参数展开及 Conv 仿真检查由对应构建入口执行。
