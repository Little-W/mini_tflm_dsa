# NPU 任务接收资格

`npu_task_accept_qualify` 组合汇总故障，输出当前任务接收资格和向量启动事件。`o_fault` 包含所有故障来源；向量运行状态与已保存接收资格互斥时，启动条件直接使用其余当前故障和卷积任务错误。

实际控制器在接收任务的边沿清除 `task_accept_ready`；向量任务运行期间，保存资格的更新条件包含 `!run_vector`。复位后的全部可达状态因此满足 `run_vector -> !task_accept_ready`。当前周期的容量错误、共享存储错误、总线错误、矩阵完成错误及中止状态仍直接参与接收资格。未知的运行状态或保存资格采用完整四态表达式。

## 验证范围

`context.py` 从参考提交 `c42f5ff9` 和实际 `npu_top.sv` 提取原有状态更新语句、接收条件及故障表达式。它逐字节检查完整父模块的修改范围，确认状态更新和其余逻辑一致。所有非状态输入逐周期自由变化，包含故障、完成、配置、后台空闲和中止状态。

`run.py` 在两种向量能力参数与四种宏定义模式下分别完成：

- 8 项复位后互斥不变量的归纳证明；
- 8 项实际控制上下文全部输出与状态的时序等价证明；
- 4,194,304 次严格四态比较，覆盖接收、运行、完成、中止、拒绝任务及 X/Z 输入；
- 完整生产配置 NPU 的 RTL 展开与模块连接检查。

形式证明覆盖改变的控制上下文，结合完整父模块的文本组成检查验证替换。NPU 的其余数据通路由项目生产测试覆盖。

运行命令：

```bash
python test/npu_task_accept/run.py --out build/npu_task_accept
python test/npu_task_accept/measure.py --out build/npu_task_accept_measurement
```

## 控制上下文测量

相同 `physical-cost` 映射下，完整控制上下文均使用 13 个逻辑 LUT，最长寄存器组合路径由 5 级降为 4 级。映射后的组合连接遍历确认，`run_vector` 到 `vector_start_fire` 的组合路径已消除。测量中的第 4 个寄存器用于验证复位历史，实际生产控制器仍使用原有三个状态寄存器。

资源与连接检查记录在 `measurement.json`，形式、四态及完整模块展开结果记录在 `validation.json`。完整 SoC 的最终组合级数由整机测量确定。
