# Gemmini command generation

This program runs the official `gemmini-rocc-tests/include/gemmini.h` scheduling
functions on the host and records their RoCC instructions for execution by a
Gemmini RTL harness. It supports `tiled_matmul_auto()`, `tiled_matmul()`,
`tiled_conv_auto()` and `tiled_conv_dw_auto()`.

The staged official header has one change: its `fence` assembler macro calls the
trace writer. A replacement `xcustom.h` records the original instruction functions
and operands. Tiling, operand reuse, loop ordering, and configuration values come
from the official implementation. Tensor storage uses an allocated host buffer;
recorded DRAM pointers are translated to deterministic physical addresses.

## Generate commands

Use the parameter header generated by the hardware configuration being tested:

```bash
python test/gemmini_comparison/gemmini_command_trace/generate.py \
  --gemmini-tests /path/to/gemmini/software/gemmini-rocc-tests \
  --params-header /path/to/hardware/generated/gemmini_params.h \
  --params-origin hardware-generated \
  --workloads /path/to/shared/workloads \
  --out build/gemmini_commands
```

`--cases` selects workload names. `--flow ws` is the default;
`--flow os` uses the official output stationary scheduler. A repository parameter
header can be used for preparation with `--params-origin repository-default`.
The parameter origin and SHA-256 are recorded in every result. Hardware runs
must check the parameter hash against their elaborated configuration.

`--tile I J K` passes explicit tile counts to the official `tiled_matmul()`
function. Each count is measured in blocks of `DIM` elements. The official
capacity and supported-mode assertions remain enabled. Omitting this option
uses the official automatic tiler.

`--transpose a` stores the same mathematical operand as `A[K,M]` and enables
the official WS transpose-A option. `--transpose b` stores it as `B[N,K]` and
enables transpose-B. `--transpose none` uses `A[M,K]` and `B[K,N]`. The shared
workload definition and expected result remain identical across these layouts.
Layout preparation occurs before hardware timing, consistently with the NPU
weight-layout preparation. The pinned official API supports either transpose
with WS; it rejects both operands transposed together and transposed OS inputs.

`--tensor-alignment BYTES` places each tensor's physical start address on a
power-of-two byte boundary, with a minimum and default of 64 bytes. Use 128 for
the corresponding memory-layout comparison with 128-byte DMA transactions.
Each tensor retains at least 64 guard bytes. The metadata records the requested
boundary, actual physical addresses, initial memory hash and command hash.
Address placement and matrix layout preparation both occur before hardware
timing; the mathematical tensors and expected output remain unchanged.

Each case contains:

| File | Contents |
|---|---|
| `commands.txt` | Original RoCC function and operand values, plus completion fences |
| `memory.bin` | Initial input, weights, bias, output storage and guard bytes |
| `expected_s8.bin` | Shared reference output bytes |
| `metadata.json` | Physical addresses, lengths, hashes, configuration and timing interval |
| `emission.json` | Counts and parameter values reported by the compiled scheduler |

Command lines use `funct 0xRS1 0xRS2`. A line containing `FENCE` waits until the
accelerator is idle and every memory response has completed. Instructions target
the custom opcode index recorded by the generated parameter header.

The RTL harness loads `memory.bin` starting at `metadata.memory_base`. It compares
the range described by `metadata.tensors.output` with `expected_s8.bin` and checks
that other memory ranges retain their initial contents.

## Timing and arithmetic

Reset the accelerator and its memory response queues before every case. All
cases start before any operand has been loaded into scratchpad. An initial
flush and fence precede the measured commands. `emission.timed_start_record`
is the zero-based record index at which measurement starts. Measurement includes
subsequent configuration instructions, launches, DMA, computation and the final
completion fence.

The command generator does not measure RTL cycles. Host C scheduling time and
CPU instruction execution are outside this accelerator-only comparison. For
end-to-end comparisons, run each accelerator through the same host execution
environment and include its software submission time.

The common workloads use INT8 operands, INT32 bias and accumulation, repeated
bias across rows, zero points of zero, and INT8 output after nearest-even
division by 32. The power-of-two FP32 scale is exactly representable. Workload
generation verifies that integer accumulators remain within the exact FP32
integer range. The generator validates all supplied tensor hashes and checks
that scheduling does not modify host tensor bytes.

## Convolution tensors and padding

Convolution workloads set `operation` to `conv` or `dw` and provide the `conv`
object with `batch`, `input_h`, `input_w`, `input_channels`, `output_channels`,
`output_h`, `output_w`, `stride`, `input_dilation`, `kernel_dilation`, `padding`
and `kernel`. The common tensor names remain `a`, `b`, `bias` and `c_s8`.

| Operation | Input and output | Weight tensor `b` | Official scheduler |
|---|---|---|---|
| `conv` | NHWC | `[Kh, Kw, Cin, Cout]` | `tiled_conv_auto()` |
| `dw` | NHWC | `[C, Kh, Kw]` | `tiled_conv_dw_auto()` |

Both convolution paths use WS. Depthwise convolution requires equal input and
output channel counts and input/kernel dilation of one. Every depthwise launch
is checked for the hardware depthwise flag.

`padding` is the top and left padding, and output height/width are explicit.
For a 3×3 kernel and even input size, stride-two SAME_UPPER uses `padding=0`
and `output_h=input_h/2`, `output_w=input_w/2`. The official scheduler derives
the bottom and right padding from the input extent and each tile. Stride-one
SAME uses `padding=1`.

After recording commands and checking that scheduling preserved all memory
bytes, the generator runs the official CPU convolution reference and compares
every output byte with the shared expected tensor. This separate software
validation checks tensor layout, padding, rounding and saturation. Its result is
recorded as `official_cpu_reference_passed`; hardware execution and timing are
reported by the RTL harness.

## Generator tests

```bash
python test/gemmini_comparison/gemmini_command_trace/test_generator.py \
  --gemmini-tests /path/to/gemmini/software/gemmini-rocc-tests \
  --params-header /path/to/hardware/generated/gemmini_params.h \
  --params-origin hardware-generated \
  --workloads /path/to/shared/workloads \
  --out build/gemmini_command_tests
```

The host compiler uses `-fwrapv`, `GEMMINI_ASSERTIONS`, and
UndefinedBehaviorSanitizer. The tests check
a complete array tile's bounds, addresses and strides, verify partial-tile
padding, relocate physical addresses across the signed 32-bit limit, and
generate output stationary commands. Ordinary and depthwise convolution tests
cover rectangular images, strides one and two, and a depthwise batch of two.
They compare every output byte against the official CPU functions and check
per-channel depthwise weight addresses. Hardware output comparisons and cycle
measurements are performed by the RTL harness.
